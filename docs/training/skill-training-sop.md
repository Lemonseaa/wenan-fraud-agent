# 问安智鉴 Skill 训练 SOP

## 1. 目标与边界

本项目不调整基础模型参数。“训练”是指：在固定模型和固定评测条件下，根据真实失败修改反诈 Skill，并通过回归测试决定是否升级。

训练闭环：

```text
划分数据 → 建立评分标准 → 编写初始Skill → 运行基线
→ 生成挑战案例 → 确认真实失败 → 最小修改Skill
→ 回归验证 → 人工批准升级
```

必须遵守：

- 开发集用于发现问题和修改 Skill；
- 验证集用于比较候选 Skill；
- 封存测试集只在版本冻结后运行一次；
- 同一 `source_id` 或同一 `real_case_id` 关联的案例不能跨集合；
- AI不能自行批准争议标签、高风险处置和 Skill 升级；
- 每轮最多修改一个明确问题，避免无法判断改动效果。

## 2. 人工与子Agent协作规则

每个新环节都按同一方式移交：

```text
人工参与校准 → 固定规则与示例 → 子Agent批量执行
→ 独立复核 → 争议项回到人工 → 规则更新后继续
```

### 2.1 校准阶段

每个新任务先选择5～10条代表性样本。生产Agent给出草稿，人负责指出错误和边界；修改结果沉淀到模板、检查清单或评分规则，不只修正当前样本。

满足以下条件后才能批量移交：

- 输入、输出字段和通过标准已经固定；
- 至少覆盖一个正常、一个诈骗和一个信息不足样本；
- 连续3条样本没有出现新的规则漏洞；
- 人能够说明应该检查什么，而不只是凭感觉通过。

### 2.2 批量阶段

- **生产Agent：** 按已批准模板生成结果，不负责批准自己的结果；
- **审核Agent：** 独立检查来源、事实边界、标签、证据、权限和格式，只能选择通过、退回或提交人工；
- **确定性程序：** 负责数据划分、字段校验、指标计算和回归测试，程序能完成的工作不交给Agent主观判断；
- **人：** 抽查通过项，处理争议，批准规则变化和版本升级。

每批最多20条。审核Agent发现问题后退回生产Agent修改，最多循环3次；仍未通过时停止自动处理并提交人工。每批通过后人工至少抽查10%，且不少于2条。

### 2.3 必须回到人工的情况

- 两个Agent结论不一致；
- 需要改变原始标签或事实边界；
- 出现规则没有覆盖的新错误类型；
- 涉及银行信息权限、高风险处置或外部工具权限；
- Skill修改可能影响正常误报或诈骗漏报；
- 连续3次修改仍不通过；
- Agent无法给出可定位的证据。

人工处理争议后，应先更新规则和示例，再重新启动批量任务，避免后续重复出现同类问题。

### 2.4 各阶段移交方式

| 阶段 | 人工校准 | 批量执行 | 人工保留权 |
|---|---|---|---|
| 数据划分 | 理解一次分组与泄漏规则 | 确定性程序 | 审批划分报告 |
| 评分标准 | 审批字段、指标和严重错误 | 程序评分，审核Agent复核争议 | 修改评分标准 |
| 初始Skill | 逐段审查 `v001` | 生产Agent起草与检查 | 批准初始版本 |
| 基线评测 | 抽查代表性错误 | 程序批量运行 | 确认真实错误 |
| 交互案例 | 共同完成前3～5条 | 两个Agent处理剩余案例 | 审批工具和权限边界 |
| 挑战案例 | 共同校准前5条 | 攻击Agent生成、审核Agent复核 | 审批标签保持和现实性 |
| 错误聚类 | 审批首批错误类型 | Agent批量归类 | 批准新的错误类型 |
| Skill升级 | 审查修改依据和副作用 | Agent提出候选、程序回归 | 最终升级或回滚 |

## 3. 阶段一：冻结并划分数据

**为什么做：** 防止同一案例原型同时出现在训练和测试中，造成虚高成绩。

**需要理解：** 开发集、验证集、测试集和数据泄漏。

**操作：** 读取350条已审批案例。先把相同 `source_id` 或相同 `real_case_id` 的案例合并为不可拆分的来源关联组，再按组划分为开发集60%、验证集20%、测试集20%，目标约为210条、70条和70条。

划分依据按以下优先级执行：

1. 同一来源不能跨集合；
2. 同一案例家族不能跨集合；
3. 三个集合尽量保持 `fraud`、`normal`、`insufficient` 比例一致；
4. 主要 `fraud_type` 尽量在三个集合中都有覆盖；
5. 最后才追求60/20/20的精确数量。

不可为了凑够条数或类别比例拆散来源关联组。稀有诈骗类型数量不足时，报告实际分布，不复制案例补齐。

**AI负责：** 编写确定性划分程序，检查重复、来源泄漏和案例家族泄漏，统计各集合的标签与诈骗类型分布。

**人审批：** 数量偏差是否可以接受、标签和诈骗类型是否严重失衡，以及测试集是否保持封存。测试集只保存清单，不用于修改 Skill。

**产物：**

```text
data/splits/v1_split.jsonl
data/splits/v1_split_report.json
```

**通过标准：** 350条完整覆盖、无重复、来源泄漏和案例家族泄漏均为0、固定种子可重复生成；V1中每个集合的每类 `label` 与60/20/20目标相差不超过8条；能够分布到至少3个来源关联组的 `fraud_type` 必须覆盖三个集合；报告完整列出任务数、来源关联组数和标签分布。若数据结构使阈值无法满足，只能提交人工审批，不能拆组或复制案例。

## 4. 阶段二：固定任务和评分标准

**为什么做：** 如果输出格式和判断标准不断变化，不同 Skill 的结果无法比较。

**需要理解：** 分类指标、误报、漏报、确定性评测和人工评审的区别。

**操作：** 固定智能体输入、输出字段、允许使用的信息、工具权限和评分方式。

最低输出字段：

```text
decision          fraud / normal / insufficient
fraud_type        诈骗时填写类型，其他情况为空
risk_level        low / medium / high
evidence          支持当前判断的题内证据
missing_information
next_action
tool_calls
stop_reason
```

核心指标：诈骗召回率、正常误报率、信息不足识别率、证据正确率、格式通过率和越权次数。V1不只看整体准确率。

**AI负责：** 提供输出 Schema、评分程序和示例。

**人审批：** 标签含义、处置权限、哪些错误最严重，以及指标是否符合比赛目标。

**产物：** 评测规则、输出 Schema 和最小测试样例。

**通过标准：** 同一答案能由固定程序重复评分；不能确定的项目进入人工复核，而不是由另一个 Agent 随意判分。

## 5. 阶段三：编写初始 Skill v001

**为什么做：** 先建立一个可解释的起点，后续才能知道改进来自哪里。

**需要理解：** Skill、提示词、规则、工具调用条件和停止条件之间的关系。

**操作：** 编写最小 Skill，覆盖信息充分性、风险信号组合、正常业务保护、追问顺序、工具使用、风险等级和处置边界。

**AI负责：** 根据已批准规则起草 Skill 和结构检查。

**人审批：** 规则是否符合银行可见信息边界，是否把单个关键词当成结论，是否存在过度拦截或越权处置。

**产物：**

```text
skills/anti_fraud/v001/SKILL.md
skills/anti_fraud/v001/metadata.json
```

**通过标准：** 输出稳定、证据来自输入、不使用事后事实、不虚构核验结果。

## 6. 阶段四：运行基线并建立错误库

**为什么做：** 先记录 v001 的真实能力，不能修改后再补写起点。

**需要理解：** 基线、混淆矩阵、按类型统计和错误分析。

**操作：** 在开发集运行 v001；验证集只用于记录初始表现，不据此逐条改规则。

**AI负责：** 批量运行、计算指标，并把错误定位到 `case_id`。

**人审批：** 抽查错误是否由 Skill 引起，排除错误标签、题面歧义和评测器错误。

**产物：** 基线报告和确认后的错误库。

**通过标准：** 每个错误都能追溯到案例、模型、Skill版本、原始输出和评分依据。

## 7. 阶段五：建立最小交互环境

**为什么做：** 静态分类只能判断现有文字，真实智能体还要在信息不足时追问和核验。

**需要理解：** 状态、工具调用、观察结果、停止条件和权限边界。

**操作：** 从开发集中选择20条代表性案例，为其补充初始信息、隐藏信息、可用工具返回、允许处置和禁止行为。

V1只提供三个模拟工具：

```text
ask_customer
verify_channel
verify_recipient
```

**AI负责：** 搭建模拟环境并记录完整轨迹。

**人审批：** 工具返回是否现实、是否泄露事后答案、建议措施是否超出银行权限。

**产物：** 20条交互案例、模拟工具和运行日志。

**通过标准：** 智能体能够完成“初判—追问或核验—更新判断—停止”，且每次工具调用都有理由。

## 8. 阶段六：攻击 Agent 生成挑战案例

**为什么做：** 主动寻找 v001 依赖关键词、忽略信息缺失或容易误报的地方。

**需要理解：** 对抗样本、标签保持、难度变化和未来信息泄漏。

**操作：** 攻击 Agent 从开发集种子出发，隐藏明显词语、替换表达、删减信息或加入正常外观。每个种子最多生成2个候选。

**AI负责：** 生成候选、说明改了什么以及攻击的 Skill 弱点。

**人审批：** 标签是否保持、场景是否现实、是否偷偷加入事后事实或改变核心事件。

**产物：** 经审批的挑战案例。未审批候选不得进入错误库。

**通过标准：** 挑战来自合理表达变化，而不是语病、矛盾或故意删除全部可判断信息。

## 9. 阶段七：确认失败并提出最小修改

**为什么做：** 防御 Agent 答错不一定是 Skill 问题，也可能是数据或评分问题。

**需要理解：** 错误归因、错误聚类和局部修复。

**操作：** 先由固定评测器找出失败，再区分数据错误、评测错误、模型随机错误和 Skill 缺陷。只有确认的 Skill 缺陷才能推动修改。

**AI负责：** 聚类相似失败，提出候选规则及其影响范围。

**人审批：** 是否值得修改、规则是否通用、是否只是为某一道题打补丁。

**产物：** 失败簇、修改理由和候选 Skill。

**通过标准：** 每项修改都对应明确失败簇，且使用行为或关系规则，不堆积具体关键词黑名单。

## 10. 阶段八：回归验证并升级 Skill

**为什么做：** 修复一种漏报可能造成新的正常误报，必须同时检查收益和代价。

**需要理解：** 回归测试、过拟合、版本选择和回滚。

**操作：** 候选 Skill 依次运行目标失败集、正常保护集、历史回归集和验证集。自动修订最多三轮，仍有问题时交给人处理。

**AI负责：** 生成对比报告，列出修复、新增错误、指标变化和规则差异。

**人审批：** 是否接受取舍、是否允许升级、是否需要回滚。

**升级条件：**

- 目标失败得到修复；
- 诈骗召回不下降；
- 正常误报不明显增加；
- 信息不足时不强行下结论；
- 没有新增越权工具或高风险处置；
- 历史回归通过。

**产物：** 新 Skill 版本、变更说明和对比报告。

## 11. 最终测试与交付

版本冻结后，才能在封存测试集运行一次。测试结果不再用于修改当前版本；若暴露问题，记录为下一版本任务。

V1交付至少包括：数据划分、v001及候选版本、评分器、基线报告、20条交互轨迹、对抗失败与回归报告、版本变更记录。

## 12. 学习与执行节奏

每个阶段采用同一节奏：

```text
先讲清一个概念
→ 查看一个真实文件或例子
→ AI完成草稿或代码
→ 人检查关键边界
→ 运行测试并看结果
→ 人确认后进入下一阶段
```

当前从阶段一开始。数据划分报告未通过前，不编写正式 v001；基线未建立前，不启动对抗循环。
