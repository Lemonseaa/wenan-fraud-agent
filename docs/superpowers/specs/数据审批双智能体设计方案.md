# 公开案例数据加工双智能体 MVP 设计

## 1. 目标

在现有《公开案例数据加工 SOP》上增加两个相互独立的角色：

- 生产 Agent：加工新数据；
- 质检 Agent：独立复核并审批。

首版只解决一件事：让一条全新公开案例能够按照现有 SOP，从来源收集走到正式结构化数据，同时避免生产者审批自己的结果。

## 2. 核心原则

1. 生产者不能审批自己的结果。
2. 质检 Agent 与人工审批者具有同等审批效力。
3. 两个 Agent 使用独立上下文，不共享生产过程中的推理。
4. 原始来源、事实边界和最终题面都必须能够追溯。
5. 自动检查只判断确定性规则，不代替语义审批。
6. 不改变现有数据目录和业务字段。
7. 双 Agent 只处理接入后创建的新任务，不接手历史半成品。

## 3. 数据结构保持不变

所有正式数据继续写入现有位置：

```text
data/raw/public_sources/SRCxxxx/original.*
data/sources/source_registry.jsonl
data/sources/real_case_registry.jsonl
data/review/public_cases/cases/Cxxxx-Tnn.md
data/review/public_cases/structured/Cxxxx-Tnn.json
```

不新增工作流数据目录，不向 registry 增加临时字段，也不修改第一阶段 JSON 的十字段 Schema。

当前6个案例组仍处于试制和审批阶段，暂不属于只读历史基线。待这6个案例组完成最终审批，并由项目负责人明确确认冻结后，以确认时已经存在的来源、真实案件、审批稿和 JSON 作为历史基线。冻结后默认只读；Agent 创建新编号时读取当前最大编号，不能硬编码起始编号。

## 4. 两个 Agent 的职责

### 4.1 生产 Agent

生产 Agent 按 SOP 生成新任务的草稿。

允许：

- 根据本轮目标搜索和推荐候选来源；
- 保存新的原始来源；
- 新增本任务的 `SRCxxxx`、`RCxxxx` 和 `Cxxxx-Tnn`；
- 根据质检意见修改本任务创建的数据；
- 将审批状态初始化为 `pending`。

禁止：

- 修改历史基线；
- 修改已经保存的 `original.*`；
- 写入任何 `approved`；
- 补造来源没有提供的事实；
- 用下游 JSON 掩盖上游问题。

### 4.2 质检 Agent

质检 Agent 是独立审批者，只负责复核和审批，不替生产 Agent 改写内容。

允许：

- 把通过复核的现有审批字段改为 `approved`；
- 写入最终 `reviewer`、`reviewed_at` 和 `review_note`；
- 退回存在问题的步骤；
- 将无法解决的分歧交给项目负责人。

禁止：

- 直接修改事实、题面、标签或证据；
- 在形成独立判断前读取生产 Agent 的解释或结论；
- 用推测补齐来源缺失内容；
- 因来源权威而跳过事实核验。

## 5. 两个审批关口

不对 SOP 的每一步分别启动一次质检。首版只设置两个关口。

### 5.1 关口一：来源与事实层

生产 Agent 先完成 SOP 第 2 至第 6 步，所有状态保持 `pending`。

质检 Agent 在独立上下文中：

1. 先读取本轮目标和 `original.*`；
2. 独立判断来源是否可用、包含几个真实案件以及事前/事后事实边界；
3. 再读取生产 Agent 写入的两个 registry；
4. 比较两套判断；
5. 通过则批准来源、案件拆分和事实边界；不通过则退回对应步骤。

关口一通过后，生产 Agent 才能进入第 7 步。

### 5.2 关口二：任务数据层

生产 Agent 完成 SOP 第 7 至第 10 步，题面和最终状态保持 `pending`。

质检 Agent 在独立上下文中：

1. 先读取已批准的事实边界，独立判断允许进入题面的事实和合理标签；
2. 再读取 Markdown 和 JSON；
3. 检查题面、构造类型、标签、证据及两份文件的一致性；
4. 通过则完成内容审批和最终审批；不通过则退回产生问题的步骤。

## 6. 完整运行流程

```text
项目负责人确认本轮数据目标
→ 生产 Agent 完成步骤 2—6
→ 自动检查来源和 registry 格式
→ 质检 Agent 执行关口一
→ 生产 Agent 完成步骤 7—10
→ 自动检查 Markdown 和 JSON
→ 质检 Agent 执行关口二
→ 再次自动检查
→ 正式完成或提交争议
```

第一版一次只处理一个新任务，不并发分配编号或写入 registry。

增强案例和正常对照不强制生成。忠实改写必须生成；其他类型只有在存在明确训练目标且能够构造可信边界时才生成，不生成时不占号。

## 7. 自动检查器

自动检查器负责：

- JSON 和 JSONL 能否解析；
- ID 格式、唯一性、文件名和正文编号是否一致；
- `source_id`、`real_case_id`、`case_id` 关联是否正确；
- 原始文件是否存在；
- 必填字段、枚举和状态是否合法；
- JSON 是否严格保持现有十字段；
- Markdown 与 JSON 的题面、标签、类型和证据是否一致；
- 每条证据能否在题面中定位；
- 是否出现明显手机号、身份证号或银行卡号；
- 本任务是否修改了历史基线。

自动检查器只能报告以下问题，不能自行作出结论：

- 来源是否可靠；
- 案件如何拆分；
- 事实属于事前还是事后；
- 是否存在答案泄漏；
- 改写是否忠实；
- 构造类型、标签和证据是否合理。

这些判断必须由质检 Agent 完成。

## 8. 退回与争议

质检结果只使用三种状态：

- `pass`：通过并写入对应的 `approved`；
- `return`：指出问题、原文依据、退回步骤和通过条件；
- `escalate`：同一语义问题连续返工三次仍无法达成一致，停止自动循环并交给项目负责人。

生产 Agent 只能修改本任务创建的数据。返工涉及事实边界、题面或标签时，质检 Agent 必须重新独立复核。

运行中断后保留已有的 `pending` 数据，不自动接管或恢复。是否继续该任务由项目负责人明确决定。

## 9. 历史数据保护

- 只有项目负责人已经明确确认冻结的历史基线默认只读；
- 发现历史数据不完整时只报告，不自动补全；
- 更新共享 registry 前必须确认文件没有在读取后发生变化；
- 只能新增或更新本任务创建的 registry 记录，不能整体重建；
- 新案例必须创建新文件，不能覆盖已有案例；
- 发现未预期的工作区变化时立即停止写入；
- 不使用整仓回滚修复单条任务。

## 10. 首版实现范围

首版只实现：

1. 生产 Agent 的角色说明；
2. 质检 Agent 的角色说明；
3. 一个确定性数据校验器；
4. 校验器测试；
5. 人工触发两个 Agent 完成两个审批关口。

首版不实现自动编排程序、A/B/C 权限模式、自动升降级、跨任务质量指标、并发处理和专用恢复命令。

先用 1 条全新案例跑通，再连续验证 5 条。完成这 6 条后，根据实际成本和错误类型决定是否值得自动编排。

## 11. 验收标准

一条新任务只有同时满足以下条件才算完成：

- 原始来源存在且没有被修改；
- 来源、案件拆分和事实边界通过关口一；
- Markdown 和 JSON 通过关口二；
- JSON 保持现有十字段；
- 自动检查全部通过；
- 最终状态为 `approved`；
- 历史基线没有被修改；
- 没有新增业务数据目录或字段。

系统验收需要证明：

- 能完整处理 1 条全新来源；
- 能连续处理 5 条；
- 能退回事前/事后边界错误；
- 能阻止答案泄漏；
- 能在出现分歧时停止并交给项目负责人；
- 所有新增数据继续使用现有结构。

## 12. 实施前置条件

现有 SOP 仍把审批主体限定为人工。实施前只修改这一项治理规则：

> 只有独立审批者可以批准；生产者与审批者不得是同一主体，也不得共享生产过程中的推理上下文。独立审批者可以是人，也可以是经过授权的质检 Agent。

SOP 的数据目录、字段、十一步顺序和事实边界规则保持不变。
