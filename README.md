# 问安智鉴

**基于多源信息核验的反诈研判智能体**

问安智鉴面向银行交易前风险识别场景，在银行可获取信息有限的前提下，综合客户陈述、交易特征、账户关系和操作行为进行研判。信息不足时，系统不强行下结论，而是提出针对性问题，补充证据后再给出风险判断和处置建议。

## 一、核心问题

传统关键词和固定规则容易被新话术绕过，大模型直接判断又可能忽略证据不足、正常业务边界和操作权限。

本项目解决三个问题：

1. 银行只能看到部分信息时，如何识别真正异常；
2. 证据不足时，如何通过追问和多源核验补齐关键证据；
3. 新型骗局出现后，如何从已确认错误中形成可验证、可回滚的新能力。

## 二、研判原则

系统分别输出三个结论，不把它们混为一谈：

- **欺诈判断：** `fraud`、`normal` 或 `insufficient`；
- **交易风险：** `low`、`medium` 或 `high`；
- **处置建议：** 放行、提醒、针对性追问、加强认证、建议暂停或人工复核。

允许出现“欺诈证据不足，但交易风险较高，建议暂停并人工核验”。信息不足不等于安全，高风险也不等于已经确认诈骗。

## 三、工作流程

```text
接收银行可见信息
        ↓
标准化并标记信息来源
        ↓
提取异常信号与证据冲突
        ↓
判断信息是否足以支持结论
        ↓
信息不足时生成针对性问题
        ↓
补充信息并进行多源交叉核验
        ↓
输出欺诈判断、交易风险、证据和处置建议
        ↓
高风险结论进入规则或人工审批
```

## 四、银行信息边界

系统只使用已授权、可追溯且与当前业务相关的信息，主要包括：

- 客户主动提供的交易目的、关系和沟通内容；
- 当前交易的金额、时间、渠道、收款方和交易备注；
- 行内可用的账户关系、历史交易和风险标签；
- 设备、登录、验证、远程控制或异常操作等受控信号；
- 合规接入的黑名单、风险账户和权威反诈信息。

系统不得假设银行能够读取完整聊天记录、任意设备内容、公安侦查信息或案件最终结果。比赛原型使用脱敏数据和受控模拟信号，不代表真实生产权限。

## 五、核心能力

- **有限信息研判：** 只根据当前可见证据判断，不使用事后结果反推；
- **主动追问：** 找出影响结论的缺失信息，提出可回答、可核验的问题；
- **多源核验：** 检查客户陈述、交易行为和账户特征是否相互支持；
- **边界识别：** 区分诈骗、正常业务和信息不足，控制漏报与误伤；
- **可解释输出：** 展示证据、冲突、未知项和结论依据；
- **受控迭代：** 从确认错误中提出候选 Skill，经验证和审批后更新能力。

## 六、系统规划

### 6.1 信息接入与标准化

各类输入先转换为统一事件结构，记录信息内容、来源、发生时间、可信度和是否可核验。缺失字段保持未知，不使用默认值伪造证据。

### 6.2 证据分析

证据分析模块识别异常交易、身份矛盾、非官方流程、紧迫施压、异常收款关系和设备操作风险，并区分直接证据、辅助信号和未知信息。具体词语只能作为线索，不能单独决定结论。

### 6.3 信息充分性判断

系统先判断现有证据能否区分诈骗与正常业务。能够支持结论时进入研判；不能支持时输出 `insufficient`，同时列出缺失证据和最有价值的核验方向。

### 6.4 主动追问与交叉核验

追问必须针对当前缺口，例如身份是否通过官方渠道核实、收款账户为何变化、交易用途能否提供独立凭证。新回答与原有交易、账户和操作信号重新比对，发现一致、冲突或仍然未知的部分。

### 6.5 风险研判与处置

研判模块综合证据强度、异常组合和缺失信息，分别生成欺诈判断、交易风险和处置建议。生成式模型可以解释和建议，但暂停交易、冻结账户等高风险动作必须由确定性规则、可信业务信号或人工审批控制。

### 6.6 Skill 迭代

能力迭代采用受控闭环：挑战题生成、数据审核、智能体作答、错误确认、错误聚类、候选 Skill 生成、安全审核、隔离验证和历史回放。只有修复未见案例且没有造成严重新增错误的 Skill，才允许进入候选能力库。

### 6.7 审计与回滚

每次研判记录输入来源、模型版本、Skill 版本、证据和处置依据。数据、提示词和 Skill 均需版本化；出现误伤、漏报或越权风险时能够定位并回滚。

## 七、数据规划

### 7.1 数据分层

数据分为四层，禁止相互覆盖：

1. **原始来源层：** 保存来源编号、原始链接、发布机构、发布日期、访问日期和原文或合法快照；
2. **事实案例层：** 从原文拆分独立案件，只保留能够被来源支持的事实；
3. **任务数据层：** 将事实案例改写为诈骗、正常或信息不足的研判任务；
4. **实验数据层：** 按用途形成开发、验证、回归和封存测试数据。

### 7.2 数据类型

- **真实案例改写：** 诈骗机制来自可核验公开来源，文本经过脱敏和场景化改写；
- **正常业务对照：** 与诈骗表面相似，但具备真实、可核验的正常流程；
- **信息不足案例：** 现有信息无法安全确认诈骗或正常；
- **受控合成案例：** 用于覆盖表达变化、边界组合和能力缺口；
- **对抗案例：** 针对当前智能体弱点生成，只用于开发和验证。

合成案例不得标记为真实案例；一个公开来源衍生的多个任务不得统计为多起真实案件。

### 7.3 最小结构化字段

每条任务至少包含：

- `case_id`：稳定且唯一的案例编号；
- `source_ids`：支持该任务的来源编号；
- `construction_type`：真实改写、正常对照、人工构造或受控合成；
- `observed_information`：银行在判断时实际可见的信息；
- `label`：诈骗、正常或信息不足；
- `evidence`：支持标签的证据；
- `missing_information`：影响判断但尚未获得的信息；
- `follow_up_questions`：需要补充核验的问题；
- `risk_level`：交易风险等级；
- `recommended_intervention`：建议的业务动作；
- `review_status`：审批状态；
- `split`：开发、验证、回归或封存测试用途。

只结构化会影响研判、评估和追溯的字段，不为未来可能的需求提前堆积标签。原始来源保留后，可以在后续版本中重新提取新字段。

### 7.4 数据加工流程

```text
收集权威来源
→ 保存原文并登记 source_id
→ 拆分独立案件
→ 核验事实与银行可见信息
→ 确定任务构造类型
→ 生成诈骗、正常或信息不足任务
→ 编写参考答案和证据
→ 人工审批
→ 结构化与自动检查
→ 按来源分组切分数据集
```

### 7.5 审批要求

AI可以完成初步提取、改写和结构检查；人必须确认来源真实性、事实边界、最终标签、参考答案和高风险处置。存在争议的案例进入复核队列，不得直接进入训练或封存测试集。

### 7.6 数据隔离

- 开发数据可用于修改提示词、规则和 Skill；
- 验证数据用于选择方案，不直接生成 Skill；
- 回归数据用于检查旧能力是否被破坏；
- 封存测试集在方案冻结前不得读取；
- 同一来源的近似改写不得跨越开发集和测试集。

## 八、版本规划

### V1：基础反诈研判

完成统一输入输出、诈骗/正常/信息不足三分类、证据说明、针对性追问、风险分级和人工复核建议。建立最小数据标准、测试集和可重复运行的评估流程。

### V2：多源信息核验

接入客户陈述、交易、账户关系、收款方、设备和操作行为等受控信号；实现信息来源标记、证据冲突检查、多轮追问和核验状态管理。

### V3：受控 Skill 迭代

从经独立审核的真实错误中生成候选 Skill，完成隔离验证、正常业务保护、诈骗召回保护、历史回放、版本管理和回滚。人工编写的专家 Skill 与自动生成 Skill 必须分开标记。

### V4：银行业务干预

将研判结果连接到提醒、针对性核验、加强认证、建议暂停和人工复核等受控动作，建立权限边界、审计记录和处置反馈。

### V5：完整比赛原型

整合多源模拟数据、反诈研判、Skill 迭代、业务干预沙盒、可视化演示和完整评估，形成可复现、可解释、可审计的比赛系统。

## 九、验收标准

项目不以案例数量、Skill 数量或单次准确率作为成功标准。每个版本至少检查：

- 诈骗召回是否提高；
- 正常业务误报是否可控；
- 信息不足案例是否保持克制并提出有效问题；
- 结论是否由可见证据支持；
- 新能力是否在未见案例上有效；
- 更新是否破坏已有能力；
- 高风险处置是否遵守权限和人工审批要求；
- 数据、模型、提示词和 Skill 是否可追溯、可复现、可回滚。

## 十、项目边界

- 本项目用于比赛研究和风险提示，不构成公安、司法或银行的最终认定；
- 比赛数据和模拟信号不能代表真实银行生产环境；
- 生成式模型不得单独执行冻结账户等高风险操作；
- 自博弈和合成数据只能用于发现能力缺口，不能直接证明真实业务效果；
- 所有能力提升必须通过隔离验证、回归测试和人工审批。
